# ML pipeline

The bounce/delivery-risk model, end to end: generate → EDA → feature engineer → select →
train (ensemble comparison) → evaluate → track (MLflow) → register → monitor (drift).

**Honest scope note:** Sendrun has never sent a real email — there's no real campaign
history yet. This model trains on synthetic data generated by running realistic,
EDA-verified assumptions through a calibrated logistic model, not on independent random
labels. See [`data/generate_synthetic.py`](data/generate_synthetic.py) for exactly what's
encoded and why, and [`NEXT.md`](../NEXT.md) for the plan to swap in real data once
campaigns have actually run — the pipeline's shape doesn't change, only the data source.

## Run it

```bash
uv pip install -e ".[ml]"

# 1. Generate synthetic data + EDA
uv run python ml/data/generate_synthetic.py
uv run python ml/data/eda.py                    # fails loudly if realism checks don't pass

# 2. Train (feature selection, 3-way ensemble comparison, MLflow logging)
export MLFLOW_TRACKING_URI="sqlite:///ml/mlflow.db"
uv run python ml/training/train_bounce_model.py  # prints the model_uri at the end

# 3. Evaluate the trained model (permutation importance, calibration)
uv run python ml/evaluation/evaluate.py <model_uri from step 2>

# 4. Register + promote to "production" alias
uv run python ml/registry/promote.py <model_uri>

# 5. See drift detection work (no real production traffic exists yet — this
#    demonstrates the mechanism against synthetic drift)
uv run python ml/monitoring/drift.py
```

## Results (current)

Held-out test set, logistic regression (won on validation PR-AUC over random forest,
XGBoost, and a soft-voting ensemble of all three):

| Metric | Value |
|---|---|
| ROC-AUC | 0.842 |
| PR-AUC | 0.579 |
| Brier score | 0.137 |

PR-AUC is the metric that matters here, not accuracy — the positive class (bounced) is
~12% of the data. A model that always predicts "no bounce" gets ~88% accuracy for free
and is useless; PR-AUC does not reward that.

Top features by permutation importance: `domain`, `prior_bounces`, `prior_sends` — which
matches what the synthetic generator actually encodes as signal (see the "design
consistency check" in `evaluation/evaluate.py`, which fails loudly if the model's learned
importance doesn't roughly match the generator's intended drivers — this is what
distinguishes "the model is weak" from "the pipeline has a bug").

## Pipeline stages, file by file

| Stage | File | What it does |
|---|---|---|
| 1. Data | [`data/generate_synthetic.py`](data/generate_synthetic.py) | Recipient + campaign features, outcomes drawn from a calibrated logistic function (not independent random labels — see its module docstring for exactly why that distinction matters) |
| 2. EDA | [`data/eda.py`](data/eda.py) | Real assertions, not just printed numbers: bounce/open/click rates against realistic bounds, class imbalance quantified, missingness, a leakage audit |
| 3. Features | [`features/pipeline.py`](features/pipeline.py) | A real `sklearn.Pipeline` — `DerivedFeatures` (ratios, cold-start flag) → scale/encode. Fit once on train, reused (never refit) everywhere else, which is what prevents train-serve skew |
| 4-6. Selection + ensemble | [`training/train_bounce_model.py`](training/train_bounce_model.py) | `SelectFromModel` on random-forest importance, then logistic regression / random forest / XGBoost / soft-voting ensemble compared honestly on the same validation fold |
| 7. Tracking | same file | Every candidate's metrics logged to MLflow, not just the winner's. The full pipeline (preprocessing + selection + model, as ONE object) is logged and then **reloaded from disk** to verify it reproduces the reported test metrics — catches serialization bugs a purely in-memory check would miss |
| 8. Evaluation | [`evaluation/evaluate.py`](evaluation/evaluate.py) | Permutation importance (on the full pipeline, raw features in — not the model's internal coefficients), calibration curve (does a "0.18" risk score actually mean ~18% bounce?) |
| 9. Registry | [`registry/promote.py`](registry/promote.py) | Staged promotion via MLflow model aliasing — the API loads by `name@production`, never a run id, so promoting a new model is one call with zero redeploy |
| 10. Monitoring | [`monitoring/drift.py`](monitoring/drift.py) | PSI (feature drift) + KS-test (prediction drift), both real and tested against synthetic drift — see the scope note above for why it isn't wired to live traffic yet |

## A note on two bugs this pipeline caught in itself

Both are documented in [`../NEXT.md`](../NEXT.md) in full, but worth knowing here:

1. The feature-selection mask was computed during training but never wired into the
   *saved* pipeline — logging `Pipeline([preprocessor, model])` alone would have silently
   fed the model the full feature set instead of the selected subset at serve time. Fixed
   with `ColumnMaskSelector`, a real pipeline step, and caught by round-tripping the
   actual saved model through disk and checking its predictions matched — not by trusting
   the in-memory object.
2. That class was originally defined inside the training *script*. Pickle/skops serialize
   a class by its qualified module path, and a class defined in a script run directly gets
   serialized as living in `"__main__"` — which means something different in every
   process. A *different* script loading the same model crashed. Moved into
   `features/pipeline.py`, which is always imported by name regardless of entrypoint.

Neither would have been caught by a test that only checks the model works in the same
process that trained it — which is exactly why `train_bounce_model.py`'s own verification
step reloads via `mlflow.sklearn.load_model()` before declaring success.

## Design principles this pipeline follows

- **PR-AUC over accuracy**, always, for imbalanced classification — stated explicitly in
  the EDA report so nobody optimizes the wrong metric downstream.
- **Every heuristic/signal is named and explainable.** The spam-risk score
  (`packages/shared/preflight.py`, not in this directory but built the same way) never
  returns a bare number — every contributing signal is listed with its own explanation.
- **A risk score must be calibrated, not just rank-ordered.** AUC measures whether the
  model correctly ranks bouncers above non-bouncers; calibration measures whether "0.18"
  actually means ~18%. A UI that displays "18/100" is making a calibration claim, so
  `evaluate.py` checks it.
- **Verify the artifact that ships, not the code that produced it.** Every check in this
  pipeline that claims "the model works" reloads the actual serialized model rather than
  trusting the in-memory Python object — see the bugs section above for why that
  distinction caught two real issues.
