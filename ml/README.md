# ML pipeline

Three models, all following the same pipeline shape: generate → EDA → feature engineer →
select → train (ensemble comparison) → evaluate → track (MLflow) → register → monitor
(drift). Plus real A/B testing infrastructure.

**Honest scope note:** Sendrun has never sent a real email — there's no real campaign
history yet. All three models train on synthetic data generated by running realistic,
EDA-verified assumptions through calibrated logistic/probability models, not on
independent random labels. See [`data/generate_synthetic.py`](data/generate_synthetic.py)
for exactly what's encoded and why, and [`../NEXT.md`](../NEXT.md) for the plan to swap in
real data once campaigns have actually run — the pipeline's shape doesn't change, only the
data source.

## Run it

```bash
uv pip install -e ".[ml]"
export MLFLOW_TRACKING_URI="sqlite:///ml/mlflow.db"

# 1. Generate synthetic data + EDA
uv run python ml/data/generate_synthetic.py
uv run python ml/data/eda.py                    # fails loudly if realism checks don't pass

# 2. Train all three models (each prints its model_uri at the end)
uv run python ml/training/train_bounce_model.py
uv run python ml/training/train_engagement_model.py
uv run python ml/training/train_send_time_model.py

# 3. Evaluate (permutation importance, calibration) — bounce and engagement only;
#    send-time's evaluation is built into its training script (hour-rank correlation)
uv run python ml/evaluation/evaluate.py <bounce model_uri> bounce
uv run python ml/evaluation/evaluate.py <engagement model_uri> engagement

# 4. Register + promote each to its OWN "production" alias — see the registry
#    section below for why "own" is load-bearing
uv run python ml/registry/promote.py <bounce model_uri> bounce
uv run python ml/registry/promote.py <engagement model_uri> engagement
uv run python -c "
from ml.registry.promote import register_and_promote
register_and_promote('<send-time model_uri>', registered_name='sendrun-send-time')
"

# 5. Drift detection (mechanism only — no real traffic to monitor yet)
uv run python ml/monitoring/drift.py
```

## Results (current)

| Model | Metric | Value | Winning candidate |
|---|---|---|---|
| Bounce-risk | ROC-AUC / PR-AUC | 0.842 / 0.579 | logistic regression |
| Engagement (open probability) | ROC-AUC / PR-AUC | 0.738 / 0.717 | XGBoost |
| Send-time recommendation | Spearman rank ρ (predicted vs observed hour ordering) | 1.0 | logistic regression |

**PR-AUC is the metric that matters for bounce-risk, not accuracy** — the positive class
(bounced) is ~12% of the data. A model that always predicts "no bounce" gets ~88% accuracy
for free and is useless; PR-AUC does not reward that. Engagement's positive class (~38%
open rate) is much less imbalanced, so both ROC-AUC and PR-AUC are meaningful there.

**Send-time is evaluated differently on purpose.** Its deliverable isn't a single
probability — it's a correct ORDERING of candidate send hours for a given contact
(`ml/training/train_send_time_model.py`'s `recommend_hour()` sweeps every hour with
everything else about the contact held fixed and returns the argmax). A classifier can
have decent PR-AUC while still ranking hours poorly if `send_hour`'s marginal contribution
is swamped by a stronger feature — so the winner is picked on held-out Spearman
correlation between predicted and observed open-rate-by-hour curves, not PR-AUC.

## Pipeline stages, file by file

| Stage | File | What it does |
|---|---|---|
| 1. Data | [`data/generate_synthetic.py`](data/generate_synthetic.py) | Recipient + campaign features; bounce AND open outcomes both drawn from calibrated logistic functions, tuned independently and verified not to interfere with each other (see the "bounce model unaffected by engagement changes" check this session ran before trusting either) |
| 2. EDA | [`data/eda.py`](data/eda.py) | Real assertions: bounce/open/click rates against realistic bounds (a regeneration that overshoots — this session hit a 75% open rate once mid-calibration — fails loudly instead of silently training on garbage), class imbalance quantified, a leakage audit |
| 3. Features | [`features/pipeline.py`](features/pipeline.py) | A real `sklearn.Pipeline`, shared by all three models — `DerivedFeatures` (ratios, cold-start flag) → scale/encode, plus `ColumnMaskSelector` (see the bugs section below for why it lives here specifically) |
| 4-8. Selection, ensemble, tracking | [`training/train_bounce_model.py`](training/train_bounce_model.py), [`training/train_engagement_model.py`](training/train_engagement_model.py), [`training/train_send_time_model.py`](training/train_send_time_model.py) | `SelectFromModel` on random-forest importance (bounce/engagement only — send-time keeps all ~10 raw features since `send_hour` is load-bearing by construction), 2-3 candidates compared honestly on the same validation fold, every candidate's metrics logged to MLflow, the full saved pipeline **reloaded from disk** before declaring success |
| 9. Evaluation | [`evaluation/evaluate.py`](evaluation/evaluate.py) | Parameterized by model kind (`bounce`/`engagement`) — permutation importance + calibration curve, plus a design-consistency check per model's own expected signal sources |
| 10. Registry | [`registry/promote.py`](registry/promote.py) | Staged promotion via MLflow model aliasing, **one registered name per model** (see the bugs section — this was originally shared and it broke) |
| 11. Monitoring | [`monitoring/drift.py`](monitoring/drift.py) | PSI (feature drift) + KS-test (prediction drift), tested against synthetic drift |
| 12. Experimentation | [`experiments/ab_testing.py`](experiments/ab_testing.py) | Deterministic per-recipient variant assignment + a real two-proportion z-test with a minimum-sample-size floor — see below |

## A/B subject-line testing

`ml/experiments/ab_testing.py` is real experimentation infrastructure, not "compare two
percentages":

- **`assign_variant(campaign_id, contact_id)`** is a deterministic hash, not a live coin
  flip — the same contact always lands on the same variant for a given campaign, even
  across a retry or a re-render. A live flip would let one contact see both variants,
  contaminating the experiment.
- **`two_proportion_z_test()`** requires both arms to clear a minimum sample size
  (100/arm) before reporting anything as significant — an underpowered test's p-value is
  not meaningful regardless of what it says. Verified against textbook cases: a 30% vs
  45% open rate at n=1000/arm is obviously significant (p < 0.001); the identical 2-point
  gap (30% vs 32%) at n=150/arm is correctly reported as "not significant," which is
  exactly the false-positive a naive "A > B" comparison would produce.

## Two real bugs this pipeline caught in itself

Both documented in full in [`../NEXT.md`](../NEXT.md), but worth knowing here:

1. **The registry originally had ONE hardcoded model name shared by all three models.**
   Registering the engagement model silently overwrote the bounce-risk model's
   "production" alias. Fixed with a `registered_name` parameter and now under direct test
   (`tests/test_ml_registry.py`) asserting the models stay genuinely independent.
2. **skops (MLflow's serializer) rejects any type it doesn't recognize as trusted** —
   correct security behavior, but it meant the FIRST successful bounce-risk training run
   (which happened to pick logistic regression) didn't reveal that the engagement model
   (which picked XGBoost on the exact same pipeline shape) would fail to log at all. Fixed
   by trusting every candidate family unconditionally, since which one wins is genuinely
   data-dependent and a script trusting only "today's winner" would fail
   nondeterministically on a future regeneration.

Also from earlier bounce-risk development (still relevant, still fixed): the
feature-selection mask was originally computed but never wired into the *saved* pipeline,
and the custom transformer class that fixed it was originally defined inside a
directly-run script, which broke cross-script loading. See `features/pipeline.py`'s
`ColumnMaskSelector` docstring for the full story — it's the reason that class lives in an
always-imported-by-name module rather than any training script.

## What's not built yet (Phase 6 remainder — deliberately deferred)

- **dbt staging → fact/dim layer** — deliberately skipped, not forgotten. Sendrun has no
  real `email_jobs`/`provider_events` history in Postgres yet; a dbt project transforming
  empty or synthetic-only tables would be decoration. Build this after real campaign
  traffic exists (see `DEPLOY.md`).
- **A real Postgres feature store with point-in-time correctness** — today's synthetic
  generator enforces this by construction (features are drawn before the per-send outcome
  loop runs, per `eda.py`'s leakage audit); a real feature store needs to enforce it by
  query once real data exists.

## Design principles this pipeline follows

- **The right metric for the actual deliverable**, not a default. PR-AUC for bounce-risk's
  imbalance, Spearman rank correlation for send-time's ordering task — accuracy is never
  the headline number anywhere in this pipeline.
- **Every heuristic/signal is named and explainable.** The spam-risk score
  (`packages/shared/preflight.py`) never returns a bare number — every contributing signal
  is listed with its own explanation, and the same principle applies to A/B testing's
  significance reporting ("not enough data yet" is a real, honest answer, not a forced
  verdict).
- **Verify the artifact that ships, not the code that produced it.** Every training script
  reloads the actual serialized model from disk before declaring success — see the bugs
  section for the two real issues that check caught.
