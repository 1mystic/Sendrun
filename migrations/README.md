# `migrations/`

Alembic, async, wired to `Settings.database_url` in [`env.py`](env.py) — migrations always
run against whatever the app itself would use (dev SQLite or a real Neon URL), one source
of truth, never a separate `alembic.ini` connection string to keep in sync.

```bash
uv run alembic upgrade head       # apply
uv run alembic downgrade -1       # roll back one
uv run alembic revision --autogenerate -m "description"   # generate a new one
```

## The `render_item` hook

`env.py` registers a custom `render_item` so autogenerate correctly imports the project's
custom column types (`GUID`, `JSONVariant` from `packages/shared/models.py`) instead of
emitting `packages.shared.models.GUID(length=36)` with no matching import — a real gap in
Alembic's default autogenerate behavior for custom SQLAlchemy types that would otherwise
produce a migration file that fails to import.

## A note on `server_default`

Alembic's autogenerate does **not** reliably detect `server_default` changes across
dialects — `0bd39148ddf7_...` was autogenerated correctly, but
`e6d7a3706d0f_add_server_default_to_provider_events_.py` was written by hand after
autogenerate produced an empty migration for a real, needed change (see that file's
`upgrade()` docstring for why the change was needed — a raw-SQL insert path bypassing an
ORM-only Python default). It also uses `batch_alter_table`, since SQLite has no
`ALTER COLUMN ... SET DEFAULT` at all — Postgres gets the direct `ALTER` via the same call.

Verified: applied, downgraded, and re-applied cleanly against a fresh SQLite DB. Not yet
run against a real Postgres instance — see [`../NEXT.md`](../NEXT.md).
